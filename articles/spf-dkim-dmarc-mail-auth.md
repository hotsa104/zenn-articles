SMTP（メール送信の仕組み）は設計上、送信元アドレスの「From」欄を誰でも自由に書き換えられる。郵便物の差出人欄を手書きで自由に書けるのと同じで、システム側は基本的にそれを疑わない。この弱点を塞ぐために作られたのが SPF・DKIM・DMARC の3点セットだ。

```
┌──────────────────────────────────────┐
│  DMARC   ポリシー適用・レポート        │  ← SPF/DKIMの結果を集約して判定
├──────────────────────────────────────┤
│  DKIM    電子署名で改ざん検知          │  ← 本文・ヘッダの署名検証
├──────────────────────────────────────┤
│  SPF     送信元IPの許可リスト          │  ← DNSに「正規の送信サーバ」を宣言
└──────────────────────────────────────┘
```

技術としては2010年代前半には確立していた枯れた仕組みだが、「導入済み」という報告と「実際に機能している」状態の間には大きな溝がある。この記事では3つの仕組みを技術的に整理したうえで、自分のドメインの設定を実際に確認する方法、そして日本企業の設定実態がなぜ「導入済みなのに機能していない」状態に陥っているのかを見ていく。

---

## ✅ 3つの仕組み

### SPF（Sender Policy Framework）

送信ドメインのDNSに「このIPアドレスからのメールだけが正規」と宣言する仕組み。

```
example.com.  TXT  "v=spf1 include:_spf.google.com ~all"
```

受信サーバは送信元IPをこのリストと照合する。`~all`（緩い失敗）か `-all`（厳格な失敗）かで挙動が変わり、`~all` のままだと不一致メールも普通に受信されてしまう。

### DKIM（DomainKeys Identified Mail）

メールに電子署名を付け、DNSで公開した公開鍵で検証する仕組み。SPFと違い**経路の途中でメールが転送されても検証できる**（SPFは転送に弱い）。

```
selector1._domainkey.example.com.  TXT  "v=DKIM1; k=rsa; p=MIGfMA0GCSq..."
```

### DMARC（Domain-based Message Authentication, Reporting & Conformance）

SPF・DKIMの検証結果を受けて「不一致メールをどう扱うか」を送信ドメイン側が指示する仕組み。ポリシーは3段階。

| ポリシー | 意味 | 効果 |
|---|---|---|
| `p=none` | 何もしない、レポートだけ受け取る | **なりすましメールは素通り** |
| `p=quarantine` | 迷惑メール扱いにする | 一定の抑止力 |
| `p=reject` | 受信拒否 | なりすましメールを実質ブロック |

**ここが最大の落とし穴**：DMARCレコードを設置しただけでは `p=none` がデフォルトであり、何も防いでいない。「DMARC導入済み」という表現は、この `none` 運用も含めてカウントされることが多い。

## 🔍 自分のドメインで確認する

自組織のドメインの設定は、DNS TXTレコードを引くだけで確認できる。

```bash
# SPF確認
dig TXT example.com +short

# DMARC確認
dig TXT _dmarc.example.com +short
```

`_dmarc` レコードが無い、もしくは `p=none` のままであれば、それは「対策済み」ではなく「入口を空けたまま」の状態にあたる。取引先や委託先のドメインでこれを確認するのも、なりすましメール調査の一次チェックとして有効だ。

受信側の実務としては、Gmail・Outlook等が表示する「認証結果（SPF/DKIM/DMARCのpass/fail）」をヘッダ情報から確認する習慣が、`none`運用の組織を騙るなりすましメールを見抜く最後の防衛線になる。

## 📊 日本企業の設定実態（Proofpoint調査、2025年12月）

上のコマンドを自社ドメインで実行すると、多くの場合「レコードはあるが`none`のまま」という結果に行き着く。これは日本企業に共通する傾向で、日本プルーフポイント株式会社が日経225企業を対象に実施した調査（[出典](https://www.proofpoint.com/jp/newsroom/press-releases/Jp-ranks-last-18-countries-effective-settings-prevent-scam-emails)）で数値として裏付けられている。

| 指標 | 2024年 | 2025年 |
|---|---|---|
| DMARC導入率（none含む） | 83% | **92%** |
| Reject設定 | 7% | 15% |
| Quarantine設定 | 13% | 21% |
| Reject＋Quarantine合計（実効防御） | 20% | **36%**（18か国中最下位） |
| None（監視のみ＝実質防御なし） | — | 56% |

国際比較でも差は明確で、Reject設定率はスイス（SMI）85%、オランダ（AEX）80%に対し、日本（日経225）は**15%**（[出典](https://www.proofpoint.com/jp/newsroom/press-releases/Jp-ranks-last-18-countries-effective-settings-prevent-scam-emails)）。

つまり「DMARC導入率92%」という見出しだけを見ると対策が進んでいるように読めるが、実際に効いている（Reject/Quarantine）のは全体の3分の1程度で、半数以上が「レコードは置いたが何も防いでいないnone運用」のまま放置されている、というのが実態だ。

---

## ⚠️ なぜ「導入済みなのに機能していない」状態が続くのか

1. **`none`から`reject`への移行は事故が怖い**：正規の外部委託先（メルマガ配信、営業支援ツール等）からのメールがSPF/DKIMに正しく対応していないと、`reject`にした瞬間に正規メールまで止まる。移行前にDMARCレポート（受信側から送られる集計データ）を数週間〜数か月分析して送信元を洗い出す必要があり、この工数を割ける組織が少ない。
2. **「導入した」の定義が曖昧**：レコードを設置した時点で対策済みとして報告が上がり、`none`のまま塩漬けになるケースが多い。
3. **効果が可視化されにくい**：防いだ攻撃の数字が出にくく、優先度が上がりにくい。

## 📊 まとめ

```
防御力
  高 │ p=reject      ██████████  ← 日本は15%のみ
     │ p=quarantine  ██████
     │ p=none        ██          ← 日本の56%はここで止まっている
  低 │ 未設置         ─
     └─────────────────────────
```

SPF/DKIM/DMARCは技術としては枯れた仕組みで、`dig`一発で自組織の状態を確認できるほど検証コストも低い。ボトルネックは技術ではなく「reject移行の運用コスト」に移っている、というのがこの分野の現在地だ。
