Galah は LLM を使って HTTP リクエストへの応答を動的に生成するハニーポットだ。任意のパスへのリクエストに対して、それらしいレスポンス（ヘッダ・ボディ）を LLM に生成させる。手作業でアプリを模倣する従来型ハニーポットと違い、事前に想定していないパスへのアクセスにもそれらしく応答できるのが売りだが、これは「1リクエスト = 1回の LLM 推論」というアーキテクチャでもある。

開発元自身がこの点を README で認めている。

> Galah was developed as a fun weekend project to explore the capabilities of LLMs in crafting HTTP messages. [...] To protect against Denial of Wallet attacks, be sure to **set usage limits on your LLM API**.

ここで断っておくと、README には「本番運用は非想定」といった明示的な文言はない（production という単語自体が一度も出てこない）。ただ筆者の考えでは、無差別スキャンが常時降り注ぐ実インターネットに、コスト制御なしで置いていい代物ではないと思う。Galah 自身もこれを見越してレスポンスキャッシュを実装している。しかしその有効性は主にラボ環境で語られており、無差別スキャンに晒され続ける実インターネット環境での長期挙動はほとんど報告がない。

自分は EU / US / SGP の3拠点で、最長77日間 Galah を運用してきた。この記事は、その全ログとキャッシュDBを解析して得た結果をまとめたものだ。

**先に結論を書く**。77日間の累積ヒット率は拠点によって58〜76%だが、これはキャンペーンの汚染込みの数字だ。汚染前の平常時に絞ると8割〜9割台まで上がる。つまりキャッシュ自体は機能しているが、単一のトラフィックキャンペーンの到来によって、ヒット率が60%台へ構造的に押し下げられている。このキャンペーンはリクエスト単位で一意な高エントロピートークンをパスに埋め込んでおり、キャッシュキーの正規化をどう工夫してもほとんど救えない。**LLMハニーポットの運用コストを決めているのは、トラフィック総量でもキー設計でもなく、少数のパスランダム化キャンペーンの有無だった。** さらに、このキャンペーンの送信元を他のハニーポットやAbuseIPDBまで追いかけたところ、正体不明のプロキシスキャン群らしき影が見えてきた——その過程も含めて書く。

> "evaluations show only incremental progress in **real-world deployments**"

[2] は HTTP 系 LLM ハニーポットの評価フレームワークとしてはよくできているが、あくまでラボ環境でキャッシュは扱っていない（実際、全文を確認すると "system-level enhancements could include caching" と、Limitations節での将来課題として触れているだけだった）。[3] は実インターネット展開だが SSH で14日間。[4] は実インターネット・3ヶ月だが SSH で、主眼は「AI駆動攻撃の検出」であってコスト経済性ではない。

**「HTTP × 実インターネット × 77日間 × キャッシュ経済性」という組み合わせは、まだ誰も報告していない。**

なお [2] Honeyval はコスト非対称性そのものは主要な実験として定量化済みだった（"our cost estimates are highly conservative" と著者自身が明記する、短時間対話・キャッシュなし前提での見積もり）。この記事の差別化点は、そこに「キャッシュを組み込んだ、実インターネットでの長期運用」を足した部分にある。

## 測定環境

| 項目 | 内容 |
|---|---|
| ソフトウェア | Galah（LLM HTTP ハニーポット） |
| バックエンドLLM | claude-haiku-4-5 |
| 待受ポート | 80 / 8888 / 9999 |
| キャッシュ設定 | `--cache-duration=-1`（無期限） |
| キャッシュキー | `port + "_" + r.URL.String()`（完全一致・正規化なし） |
| 拠点 | EU1 / US1 / SGP1-HNP |
| 観測期間 | 最長77日（2026-06-04〜08-19） |

キャッシュを最大限有効化した状態での計測である点は先に断っておく。「設定が甘かっただけ」という話ではない。

## 結果1: 累積ヒット率は「上がって終わり」ではなかった

77日間の累積で見ると、ヒット率は次の通り。

| ノード | cache | llm | LLM失敗 | ヒット率 | 観測日数 |
|---|---|---|---|---|---|
| EU1 | 32,015 | 7,932 | 2,237 | **75.9%** | 最長（〜77日） |
| US1 | 25,381 | 9,967 | 2,448 | **67.2%** | 77日 |
| SGP1-HNP | 12,244 | 8,909 | 32 | **57.8%** | 24日 |

LLM 生成に失敗したリクエストはキャッシュミス側に計上している（キャッシュを引けずに LLM へ投げて、失敗したものだから）。これを除外すると約5ポイント過大評価になる。

この表は**77日間全体の累積値で、後述するキャンペーンの汚染期間を含んだ数字**である。後半で紹介する「平常時86.5〜91.2%」等は、汚染されていない特定の日だけを取り出した日次値で、別の量を測っている。累積値の方が低く出るのは当然だが、説明なしに並べると矛盾しているように見えるので先に断っておく。

同一ノードの時系列を見ると、単純な右肩上がりではないことがわかる。

| ノード | 2026-06-04 | 2026-08-20 |
|---|---|---|
| EU1 | 47.98% | 75.9% |
| US1 | 70.31% | 67.2% |

EU1 は上昇しているが、US1 は**下落している**。2点だけを見て「キャッシュは育つほど効く」と結論づけたくなるが、それは半分しか合っていない。

実際には性質の異なる2つの効果が混ざっている。

1. **前半（6月〜8月上旬）**: キャッシュがまだ育っていない初期はヒット率が低い。これは素直な蓄積効果で、幻想ではない。
2. **後半（8月中旬以降）**: 十分に蓄積が進んだ後もノード間でヒット率に差が残るのは、蓄積日数の違いではなく、後述するキャンペーンの混入率の違いによるもの。

US1 が正味で下落しているのは、この2の効果が1の効果を打ち消して余りあるほど強いからだ。EU1 はキャンペーンの混入率が低かったので上昇がそのまま見えている。

## 結果2: 新規キーの発生は減衰しなかった

キャッシュが育てば新規キーの発生は減っていくはずだ、と最初は予想していた。US1 の日別新規ユニークキー数を見ると、そうはなっていない。

```
2026-06-12   26     2026-07-15   18     2026-08-12  1240
2026-06-15   32     2026-07-22   26     2026-08-13  1205
2026-06-18   30     2026-07-27   18     2026-08-14   987
2026-07-02 5608     2026-08-02   30     2026-08-15  1070
2026-07-11 3717     2026-08-05   46     2026-08-16   941
2026-07-13   27     2026-08-08 1143     2026-08-18  1015
```

38,568キーを蓄積した8月中旬でも、日次1,000件前後の新規キーが発生し続けている。「スキャナーのパス空間は無限に薄く広がっている」という直感的な説明にも見えるが、これは間違いだった。

新規キー率（新規キー数 ÷ 総リクエスト数）を時期で分解すると、トラフィック量の増加では説明できない跳ね方をしている。

| ノード | 8/12以前の新規率 | 8/12以降の新規率 |
|---|---|---|
| US1 | 6〜12% | **23〜38%** |
| EU1 | 2〜14% | **19〜33%** |
| SGP1-HNP | 11〜21% | **39〜52%** |

3ノード同時に跳ね上がっている。US1 の 8/12 以降の新規キー 8,025件をパスの第1階層で分類すると：

| パス第1階層 | 件数 |
|---|---|
| **`/c`** | **6,663（83%）** |
| `/.git` | 95 |
| `/api` | 76 |

**単一のキャンペーンが、新規キーの大半を生み出していた**（US1 83% / SGP1-HNP 84% / EU1 59%）。EU1 の混入率だけが低く、これがそのまま EU1(75.9%) と US1(67.2%) のヒット率差の説明になる。

実キー例はこんな形をしている。

```
9999_/c/poq-YRNzIQGzL78zd6wix-gi4zci6n3QqBw1eH5YmsevLW8zaAumVvEDFWAF8CVaxndKwNF2Sqdbn3ZUZGsw6-8rfqaQL1mTIi63j24
```

このキャンペーン（US1 側で6,744リクエスト）の特徴を挙げる。

- 送信元は `151.243.11.0/24` と `45.194.67.0/24` に分散（個別IPのレート制限を避ける水準の分散度）
- User-Agent は全リクエストで同一
- GET のみ、ポート 8888/9999 のみ（80には一切来ない）
- 08-11 開始 → 08-12 に立ち上がり → 以後 800件/日前後で定常

**これは脆弱性スキャンではない**、というのが調べていて一番意外だった点だ。

- ヘッダが Chrome のものと完全一致（`Accept`, `Upgrade-Insecure-Requests` など）
- トークンは拠点間でほぼ重複しない（US1∩EU1で1件、あとは0）— 固定リストの再生ではなく生成されている
- トークンは100/103文字の base64url。復号すると75〜77バイトの不透明バイナリ
- リクエストターゲットは origin-form で、古典的なオープンプロキシ探索とも違う

正体は完全には特定できなかったが、以下の2つの追加調査でかなり絞り込めた。ただし1点、最初に手がかりになった事実がある。**port 80には一切来ず、port 8888/9999にのみ来る。** これは「無差別に発見された」のではなく、あらかじめこの IP:port の組み合わせを知らされていたことを示唆する。

### ハニーポット全体を横断して確かめる

ここまでは Galah 自身のログだけを見た話だ。Galah の応答生成が絡む以上、この特徴付けが LLM 側のバイアスを引きずっていないか気になったので、もう一段掘った。

このキャンペーンの送信元IP（US1側で70個）を抜き出し、**Galah以外の全ハニーポット種別・全3拠点・全77日間**で横断検索した。P0f（受動的フィンガープリンティング）と Suricata（IDS）はホスト宛の全トラフィックを無条件に記録するので、Galah のログには現れない挙動があればここに出るはずだ。

結果は次の3点。

- **Cowrie・Dionaea・RDPHoneypot・Honeytrap など、ペイロードを捕獲する系統のハニーポットには一件も出現しない**。出現するのは P0f と Suricata だけ
- **私たちの3拠点に対する宛先ポートは 8888 と 9999 のみ**。80番はもちろん、SSH・RDP・SMB 等どのポートにも一切現れない（後述するAbuseIPDBの通報を見ると、他所の被害者に対しては443や1080等の別ポートでの挙動も報告されている——私たちに対してだけこの2ポートに絞られている、という点が重要）
- **時系列がきれいに揃う**: 私たちの3拠点への観測では 08-11 以前は活動ゼロ、08-11 に US1・EU1・SGP1-HNP の3拠点で同時に立ち上がる（port 8888/9999限定で再検証済み、無条件の全ポート集計でも同じ結果だった——後述する通りこのIP群は元々この2ポートにしか来ていない）

これは Galah のログだけでは言えなかったことだ。もし正体がただの無差別スキャナーなら、同じIPが他のポート・他のハニーポットにも多少は触れているはずだが、そういう痕跡は一切ない。**Galah の2ポート以外にはまったく興味を示していない**、という狙い撃ちの度合いが、LLMの応答生成を介さない独立したソースから裏付けられた形になる。

副産物として、08-15以降このIP群のSGP1-HNP側の件数だけが激減している点も確認できた。これは本稿を書いている最中に発覚した別件のインフラ障害（SGP1-HNPが設定ミスで7日間ほぼ全ハニーポット停止していた）の期間と正確に一致しており、データの整合性チェックにもなった。

### AbuseIPDB照会 — この送信元は「いつから」知られていたのか

もう一段、外部の視点を入れてみた。70個の送信元IPを AbuseIPDB（IPレピュテーションの共同データベース）に照会し、他の被害者からの通報履歴を確認した。

結果は次の通り。

- **70件中65件（93%）の初回通報が、2026-08-06〜08-12 の1週間に集中していた**。特に08-08だけで35件（全体の半分）が初通報を受けている
- それ以前の通報履歴を持つのはわずか4件（2026-01-25/02-25/02-25/02-26。いずれも他の被害者からの通報で、**私たち自身の3拠点では08-11より前にこのIP群からの着信は一件もない**——同じIPが他所ではもっと早くから活動していたが、私たちのノードに対して動き始めたのは08-11から、ということになる）
- 通報カテゴリの内訳は **Port Scan（3,432件）と Open Proxy（3,274件）がほぼ同数で上位2つ**、次いで Web App Attack・DDoS Attack・Brute-Force と続く
- 全件が `usageType: Data Center/Web Hosting/Transit`（住宅回線ではなくデータセンター系IP）

これは重要な情報だ。**この送信元帯は、私たちが `/c/` を観測し始めた時期（08-11）とほぼ同時に、他の被害者からも初めて通報され始めている。** 半年以上前から知られた常連の悪性IPがたまたま私たちにも来た、というより、**この時期に新規展開されたばかりのフリートに、展開直後から巻き込まれた**と考える方が筋が通る。

さらに、通報の**コメント本文**を読むと推測ではなく具体的な挙動が書かれていた。

> Detected by SentinelX honeypot: sent HTTP CONNECT request probing for an open proxy. Connection was hijacked and held in a tarpit to slow down the scan. Probed target: tls.bunnyfeet.baby:443

同じ送信元から、`we-love-the.world` 等の別ドメインへの同種の CONNECT プローブも複数報告されていた。**この `151.243.11.0/24`（キャンペーンの片方の/24。もう一方の `45.194.67.0/24` は対象外）は、実は8/19の別件調査（Galahのレート制限対策を見直した際）で既に一度遭遇していた**。そのときは Galah 自身ではなく別ノードの挙動として「`bunnyfeet.baby`・`we-love-the.world` 等へのCONNECT＝オープンプロキシ検査ボット」と特定していた。AbuseIPDBという外部ソースが、社内の以前の調査と独立に同じ結論を裏付けた形になる。

ただし正確を期すなら、**Galahに対する挙動とAbuseIPDB上の挙動は同一ではない**。他所の報告はHTTP CONNECTメソッドでのプロキシ中継検査だが、Galahが受けたのはGETメソッド・origin-formの`/c/<token>`だった（§4で確認済み）。素直に読むなら、**同一の運用者・同一のツール群が、宛先ポートに応じて異なるプローブ手法を使い分けている**——8888/9999のような「プロキシソフトの既定待受ポート」として知られるポートには軽量なGETでの生存確認、それ以外のポートにはCONNECTでの中継検査、という役割分担が最も自然な説明に思える。リクエストごとに変わる不透明トークンは、キャッシュされた古い応答を「生きている」と誤判定しないためのキャッシュバスターと考えれば筋が通る——皮肉なことに、これはまさに Galah のキャッシュを壊した仕組みそのものでもある。

完全な断定はできない。ただし「アドテックの残留トラフィック」説より、**「新規展開されたプロキシプールを検証する多目的スキャンツール」**という説の方が、AbuseIPDBの通報コメントという独立かつ具体的なソースの裏付けを持つ分、有力になったと言える。

### `/c/` は唯一の異常ではなく、27件のバースト群の中の外れ値だった

ここまでの話には弱点がある。「たまたま一度だけ観測された異常では」という反論だ。実際、77日間を通してよく見ると、新規キーの急増日（>200件/日）自体は珍しくない。US1・EU1でそれぞれ26〜29日、散発的に起きている。

US1の生ログは08-05以前がローテーションで消えているため、`/c/` 以外の26〜29件についてはUA・送信元IP・CIDR分布までは遡れない。使えるのは cache.db に残るキー（ポート＋パス）だけなので、そこで全ての急増日を、①最多パス第1階層への集中率、②パス末尾トークンが高エントロピーな不透明文字列である割合、の2軸で判定した。

| | `/c/` 期間（8/12〜19、9日連続） | それ以外の急増日（26〜29日、散発） |
|---|---|---|
| 最多パスへの集中率 | 70〜96% | 最大でも約40%、大半は数%〜20%台 |
| 末尾トークンのopaque率 | 70〜96% | ほぼ0% |
| 継続日数 | 9日以上（ログが残る最終日でも継続中） | 最長4日 |
| 典型パターン | `/c/<opaqueなトークン>` 単一 | `/admin` `/.git/HEAD` `/.aws/credentials` `/.jenkins` 等、数十のディレクトリに分散した組み合わせ的な走査 |

:::message
①集中率と②opaque率は、独立した2つの証拠ではない。`/c/` 期間の各日ではこの2つの値はほぼ同一になる（例: US1 08-12は90.3%/90.3%、EU1 08-13は92.2%/92.2%）。`/c/` が単一パスに集中し、かつそのパスの末尾がopaqueだから当然どちらの軸で測っても同じ値になる——1つのシグナルを2つの指標で見ているだけで、判定の裏付けとしては1本分と捉えた方が正確だ。
:::

実際、以前は「未説明のスパイク」として保留していた7/02・7/11・8/08のイベントも、この分類にかけると全て`/c/`とは別系統（分散型・非opaque）だった。7/02は`/admin`に最大10.9%集中・opaque率0%、7/11は`/config`に最大11.6%集中・opaque率0%、8/08は`/catalog`に最大20.9%集中・opaque率2.2%——いずれも`/c/`の70〜96%とは1桁近く違う。

**「`/c/`だけが特別」なのではなく、「同一センサー群で77日間に27件前後観測されたバースト群の中で、`/c/`だけが集中率・持続性の両方で突出している」**、という形でようやく言える。n=1の弱さを、n=27の対照群に対する外れ値という形に置き換えられた。

## 平常時のヒット率はどのくらいだったのか

さきほど「平常時は8〜9割台」と書いたが、この数字にはやや薄い根拠しかない。ログが両ノードで重なる、キャンペーン前の窓は 2026-08-05〜08-11 のわずか6日間しかない（US1の生ログはそれ以前がローテーションで消えている）。

| date | US1 ヒット率 | EU1 ヒット率 | 備考 |
|---|---|---|---|
| 08-05 | 89.6% | 49.9% | EU1はバースト混入 |
| 08-06 | 34.6% | 95.2% | US1は失敗集中（後述） |
| 08-07 | 86.5% | 85.3% | |
| 08-08 | 39.7% | 81.5% | US1はバースト混入 |
| 08-09 | 89.2% | 97.1% | |
| 08-10 | 91.2% | 94.6% | |
| 08-11 | 78.2% | 87.4% | キャンペーン開始日 |

SGP1-HNP は全期間を通してヒット率の変動が大きく、「クリーンな日」を切り出せる帯自体が存在しないため、この節ではUS1/EU1のみを扱う。汚染日（US1: 08-06・08-08、EU1: 08-05）を除いた「真にクリーンな日」だけで見ると、US1は4日で **86.5〜91.2%**、EU1は5日で **81.5〜97.1%**。どちらも高い水準で、キャッシュ自体は十分に機能していると言える。8/11 を含めるかどうかで下限が78%から86.5%まで動くくらい、この窓は薄い——この点は自分から明記しておく。

## 結果3: キー正規化はどこまで救えるか

「キャッシュキーの粒度が甘かっただけでは」という反論を先回りして検証した。cache.db 全38,052件の一意キー（**3ノード合算**）に、正規化のレベルを段階的に上げながら適用した結果が以下。

| 正規化レベル | 一意キー数 | LLM呼出削減率 |
|---|---|---|
| 完全一致（現行 Galah） | 38,052 | — |
| + クエリ除去 | 35,566 | 6.5% |
| + URLデコード | 33,952 | 10.8% |
| + 数値/UUID/長hex抽象化 | 32,900 | 13.5% |
| + パス2階層クラスタリング | 26,772 | 29.6% |
| + パス1階層クラスタリング | 9,993 | 73.7% |

最初は「クエリ文字列がランダム化されているのだろう」と予想していたが、逆だった。ランダム化されているのはクエリではなく**パスそのもの**で、クエリ除去・URLデコード・数値抽象化はいずれも原理的に効かない。

さらに、コストを支配する時間帯（キャンペーン到来後の8/12以降）に絞ると、正規化の効果はほぼ消える。以下は**ノード別**の内訳（上表の3ノード合算とは母集団が異なる点に注意）。

| ノード | 期間 | +クエリ除去 | +URLデコード | +数値抽象化 |
|---|---|---|---|---|
| US1 | 全期間 | 6.5% | 10.8% | 30.4% |
| US1 | 08-12以降 | **1.8%** | **2.6%** | **3.3%** |
| EU1 | 全期間 | 8.3% | 11.2% | 21.4% |
| EU1 | 08-12以降 | **1.2%** | **1.3%** | **1.9%** |
| SGP | 全期間 | 3.5% | 3.5% | 12.0% |
| SGP | 08-12以降 | **3.6%** | **3.6%** | **10.1%** |

粒度を上げても、コストが実際に発生している窓では 1.2〜3.6% しか救えない。73.7% まで削減しようとすると、パスを1階層に畳む必要があり、それはレスポンスの固有性を失うことと同義になる。**キー正規化は解決策にならない。有効な対策があるとすれば、キャンペーン検出の方だ。**

## 実請求額での裏付け

ここまではログの集計値だった。独立したソースとして、Anthropic Console の日次課金データ（claude-haiku-4-5、単一APIキー、他用途との混在なしを確認済み）も見てみた。

| 期間 | 平均日次コスト |
|---|---|
| 平常期（8/01〜8/10） | **$0.77/日** |
| キャンペーン期（8/11〜8/20） | **$4.08/日** |
| 倍率 | **5.28倍** |

期間合計 $48.57（8/01〜8/20）。ログ側の新規キー率分解（US1 6〜12%→23〜38% 等）とは完全に独立したソースからも、同じ「単一キャンペーンがコストを支配する」という結論が出た。集計方法のアーティファクトではなく、実コストとして裏付けが取れたことになる。

## 結果4（副次）: 生成失敗は「定常的な指紋」ではなかった

LLM 生成に失敗すると Galah はそのまま 500 Internal Server Error を返す。これ自体は検知面になり得る（普通の Web サーバーは500をこんなに頻繁には返さない）が、失敗率自体を見ると US1 6.5%・EU1 5.2% と、一見「定常的な背景率」に見える。

日別に分解すると、そうではなかった。US1 の全失敗2,448件のうち **66%（1,621件）が08-06の1日に集中**していた。Galah のソースコードを確認すると、Anthropic API 呼び出しに10秒のハードコードタイムアウトがあり、この日のエラーはすべて `context canceled`——つまりタイムアウト超過だった。UA は多様な偽装ブラウザ群でポートは80が支配的、特定の攻撃者の挙動ではなく、その日たまたま API 側のレイテンシが閾値を超えたと考えるのが自然だ。

「500を返すことが検知面になる」という主張自体は残るが、「定常5〜6.5%の背景率」という説明は誤りで、実態は「API レイテンシが閾値を超えた日に、その日の応答がまとめて500化する間欠的な障害モード」だった。

## まとめ

1. キャッシュは機能している。平常時のヒット率は US1 86.5〜91.2%・EU1 81.5〜97.1%（限られた観測窓での値）。「LLMハニーポットのキャッシュは効かない」という直感は外れていた。
2. コストを決めているのはトラフィック総量ではなく、**パスランダム化キャンペーンの有無**。単一キャンペーンが8/12以降の新規キーの59〜84%を生み、ヒット率を60%台へ引き下げていた。
3. キー正規化は解にならない。コストが実際に発生する窓では 1.2〜3.6% しか削減できない。ランダム化されているのがパスそのものである以上、原理的に救えない。
4. したがって「1リクエスト=1推論」というアーキテクチャの運用可否は、キャッシュ設計ではなく**キャンペーンをどれだけ早く検出・遮断できるか**にかかっている。

実装への提言としては、URLデコード正規化は低コストかつ他への悪影響がなく（+4.3ポイント程度は稼げる）上流への提案候補になる。パスクラスタリングは、応答の固有性を捨てる覚悟がある運用者だけが選ぶべきトレードオフだ。生成失敗時のフォールバック応答（静的な404など）を用意しておくと、500の素通しという指紋を減らせる。

## 検証中の話

このキャンペーンが「本当にキャンペーン」であることを一番強く示せるのは、それが終息した後にヒット率が平常水準（US1 86.5〜91.2%・EU1 81.5〜97.1%）へ回復するかどうかだ。現在 EU1/US1 の観測を継続しており、結果が出次第この記事に追記する。
